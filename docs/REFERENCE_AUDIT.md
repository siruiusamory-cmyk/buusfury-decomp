## 2. Coverage inventory - semantic source vs opaque

The decisive finding: **this project is a repackaging harness, not a semantic
decompilation.**

```
asm/rest_of_the_game.s  (16 lines, the whole file)

    AREA Other, CODE, READONLY
        INCBIN      baserom.gba_0x06d4e0_0x071758.extracted
        INCBIN      build\asset_dialogbox.compressed
        INCBIN      build\asset_dialogbox_small.compressed
        INCBIN      baserom.gba_0x071c90_0x3be3d4.extracted
        INCBIN      build\asset_splash.compressed
        INCBIN      baserom.gba_0x3c33f8_0x7b89a8.extracted
        INCBIN      baserom.gba_0x7b89a8_0x800000.extracted
    END
```

`build.bat` extracts **ten** ranges straight out of `baserom.gba`. Those ranges
plus the header/data regions total **8,268,480 bytes - 98.568% of the image** -
copied verbatim and never disassembled.

Within the 120,440 reconstructed bytes:

- **Real executable-code source is ~5,020 bytes: 0.060% of the ROM.**
  (`crt0.s` 152 + `GBARam.s` 232 + `AfterLibs` 12 + `color_transforms.cpp` 4,608)
- `strings.cpp` is the largest single item at 1.06% of the image, and it is data.
- The remaining 26,112 bytes are image/palette assets regenerated by grit and
  JCALG1 - reproducible without ADS 1.2, and independently verified here.

## 3. Findings that change how we build

### 3.1 The comparison is disabled

```bat
:: Comparing Images :::
::call fc /b "baserom.gba" "image.gba"     <-- commented out at build.bat:62
call tools\sha1.bat image.gba
```

The reference build **never fails on a mismatch**. It prints a hash and deletes
`build/`. Any claim that its output matches is unverified unless a human reads the
printed hash. Our pipeline fails closed instead.

### 3.2 The original compiler flags survive in one comment

```asm
; asm/GBARam.s:5
; tcpp -S -c -cpu ARM7TDMI -O1 src/GBARam.c
; For now, just assembly because of alignment issues.
```

This is the only surviving statement of the original toolchain's behaviour, and
it is the highest-value input for `DECOMP-COMPILER-PROBE-001`:
compiler `tcpp`, CPU `ARM7TDMI`, optimisation `-O1`, output assembly (`-S`).
Note the annotation: the function was transcribed by hand "because of alignment
issues", so even this region was not reproduced by compiling.

### 3.3 `armcpp` is invoked with no optimisation flag

```bat
armcpp -c src/color_transforms.cpp -o build/color_transforms.o
armcpp -c src/strings.cpp          -o build/strings.o
```

Whatever ADS 1.2 defaults to applies. For `strings.cpp` this is almost certainly
harmless (it is data), but for `color_transforms.cpp` it determines the emitted
`.constdata` layout. Open question for the compiler probe.

### 3.4 `wchar_t` width is an unguarded compiler assumption

`strings.cpp` declares `wchar_t u_Start_0805792e[] = L"Start";`. The ROM's string
pool is **UTF-16LE**. Under ADS 1.2 `wchar_t` is 2 bytes, so the encoding is
correct by accident. Under a compiler with 4-byte `wchar_t` the file encodes
UTF-32 and the build silently produces the wrong bytes. There is no assertion.

### 3.5 The CMake step is generator-dependent

`build.bat` configures with `-DCMAKE_BUILD_TYPE=Release` but then runs
`tools/compress/build/Debug/compress.exe`. This works only because the Visual
Studio generator is multi-config and ignores `CMAKE_BUILD_TYPE`, defaulting to
`Debug`. With the MSYS2/MinGW CMake that devkitPro installs, the configure step
fails outright:

```
CMake Error: Could not create named generator Visual Studio 17 2022
```

Verified on this machine. The harness therefore resolves the VS-bundled CMake
explicitly and reports the failure mode by name.

### 3.6 The link silently depends on `-noremove`

`ewram.s` and `iwram.s` contain only `SPACE` reservations in `+RW` regions. Without
`-noremove`, `armlink` discards them and the image no longer reaches the fixed
section addresses.

### 3.7 `opaque_10` is mislabelled

`build.bat` calls `0x7B89A8-0x800000` "`<null bytes>`". Measured: all **292,440**
bytes are `0xFF`; there are **zero** non-`0xFF` bytes. The label is wrong and the
range is **not proven unused** - LOG1-REMAKE's TOOLKIT-011 measured 516
pointer-shaped little-endian `u32` values pointing into it and refused to promote
it to free space. Do not treat it as free space without ownership evidence.

### 3.8 Smaller hazards

- `tools/incbin.bat` writes `baserom.gba_<start>_<end>.extracted` into the
  **repository root** and **skips if the file already exists** - stale inputs are
  reused silently.
- `tools/incbin.bat` requires Windows PowerShell 5.1: `Get-Content -Encoding Byte`
  is invalid in `pwsh` 7.
- A filename is misspelled upstream: `assets/cornet_top_left.bmp`. Reproduced
  exactly here, because it is load-bearing.
- No ADS version check anywhere; the scripts accept any `armasm` on `PATH`.
- `rmdir /S /Q build` at the end makes the build non-incremental.

## 4. Cross-checks performed against the canonical ROM

Every claim above that touches the binary was re-measured. Every `asset` region
was rebuilt from its source asset and compared.

| Check | Result |
| --- | --- |
| Ten `incbin.bat` ranges tile against the scatter addresses with no gap | CONFIRMED |
| `crt0` literal pool ends exactly at `0x000158` where the first `INCBIN` begins | CONFIRMED |
| `GBARam.s`'s own 248 bytes + its two `INCBIN`s fill `0x03D4D0-0x03D740` exactly | CONFIRMED |
| `AfterLibs` is exactly 12 bytes and ends at the next `INCBIN` | CONFIRMED |
| 4 corners × 64 bytes + 2 palettes × 512 bytes end flush at `0x05672C` | CONFIRMED |
| `asset_dialogbox` is exactly 788 bytes, matching `build.bat`'s own minimum-size argument | CONFIRMED |
| JCALG1 stream headers declare 0x9600 / 0x2800, matching grit's output sizes | CONFIRMED |
| Header checksum at `0x00BD` recomputes to the stored `0x84` | CONFIRMED |
| `0x7B89A8-0x800000` is entirely `0xFF` (0 non-conforming bytes) | CONFIRMED |
| All 10 asset regions rebuild byte-identically | CONFIRMED |

## 5. Verdict

`2genkidev/buusfury` is useful as a **map of the ROM and a demonstration of the
ADS 1.2 build path**. It is not useful as a source of decompiled code, because it
contains almost none - 0.06% of the image is executable-code source, and 98.57%
is copied verbatim from the baserom.

Its region boundaries are trustworthy and have been independently verified here.
Its licensing does not permit reuse of its expression. Its build has several real
defects, above all that **it never verifies either its input or its output**.

We therefore take from it: the region map, the tool inventory, the exact command
lines, and the surviving `tcpp -O1` evidence - and nothing else.
