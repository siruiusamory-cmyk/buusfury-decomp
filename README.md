# Dragon Ball Z: Buu's Fury Decompilation

[![progress report](https://github.com/siruiusamory-cmyk/buusfury-decomp/actions/workflows/report.yml/badge.svg)](https://github.com/siruiusamory-cmyk/buusfury-decomp/actions/workflows/report.yml)
[![semantic code](https://decomp.dev/siruiusamory-cmyk/buusfury-decomp.svg?mode=shield&measure=matched_code&label=semantic%20code)](https://decomp.dev/siruiusamory-cmyk/buusfury-decomp)

Work-in-progress decompilation and source reconstruction of **Dragon Ball Z:
Buu's Fury** for the Game Boy Advance.

> This repository contains no game data. It does not include the ROM, extracted
> graphics, audio, text, or any other copyrighted material. **You need your own
> legally obtained copy of the game** to build or verify anything here.

## About

The aim is to recover readable source code corresponding to the original game's
executable code: C that a compiler turns back into the same ARM/Thumb machine
code the cartridge holds.

That is a long road, and the project is honest about where it stands. The original
game was built with a commercial compiler that is not available here, so exact
compiler matching cannot yet be demonstrated. What the project does instead is
reconstruct each function in C, **prove its behaviour by running it against the
original instructions**, and record that evidence in the repository. Reaching
byte-for-byte builds is the goal; demonstrating semantic equivalence is the step
that can be taken today.

The work concentrates on the parts of the game that can be pinned down from the
image itself: the script virtual machine, the engine's collection and flag
machinery, and the block of ARM code the game copies into IWRAM at boot.

## Project status

Established and verified:

- canonical ROM identification that fails closed on any mismatch;
- an independent structural map of all 8 MB of the cartridge, derived from the
  image rather than from a third-party disassembly;
- a candidate function inventory for the executable regions;
- a reconstruction loop with 24 translation units of original C, each with a
  host self-check and a committed comparison against the original bytes;
- the runtime-copied IWRAM overlay, recovered and lifted;
- deterministic progress reporting, published to decomp.dev from CI.

Not yet possible:

- byte-identical builds. The original compiler (ARM Developer Suite 1.2) is
  commercial software, is not licensed on this machine, and its input sources
  cannot be redistributed. Every reconstruction therefore carries three separate
  verdicts - behaviour, modern build, and original-compiler match - and only the
  third is blocked.

In short:

- a function counts only once its reconstruction is **proven** to behave like the
  original - the project runs it and asserts the results, and a stub, a known
  boundary, or merely compiling does not count;
- reconstructed source is also compiled with a modern ARM toolchain to show it is
  real, buildable C, but that is **not** claimed to be byte-identical to the
  original build and earns no progress credit;
- exact original-compiler matching is tracked as a separate, currently blocked
  concern.

## Supported version

| | |
| --- | --- |
| Game | Dragon Ball Z: Buu's Fury |
| Platform | Game Boy Advance |
| Region / revision | USA, rev0 |
| Game code | `BG3E` |
| Size | 8,388,608 bytes |
| **SHA-1** | `f1c4b07554d2a3b1ad2f325307051e775ce68087` |
| CRC-32 | `01C1707F` |

Other revisions and other Buu's Fury images are **not** supported: their file
offsets are not transferable. Every entry point checks the identity above and
stops on any mismatch.

The ROM itself is never included and never tracked, and no extracted game data is
distributed with this repository.

## Getting started

Requirements: Python 3.11 or newer and Git. The analysis, build and progress
tooling is pure standard-library Python - there is nothing to install.

```powershell
git clone https://github.com/siruiusamory-cmyk/buusfury-decomp
cd buusfury-decomp

# make your own ROM available (never inside version control)
$env:BUUSFURY_ROM = 'D:\dumps\Dragon Ball Z - Buu''s Fury (U).gba'

# verify the image and run every gate that can run here
pwsh -File scripts/check.ps1
```

`scripts/check.ps1` prints one summary line per gate and reports the two gates
that depend on the unavailable commercial compiler as **BLOCKED** rather than
failing, because a documented blocker is a result.

## Building / validation

Nothing in this project needs a ROM except the gates that compare against the
original image. The repository's own CI runs the progress report with no ROM, no
compiler and no build output present.

```powershell
$env:PYTHONPATH = "$PWD\tools"

python -m buusfury status     # every achievable gate, one summary
python -m buusfury verify     # canonical ROM identity, fails closed
python -m buusfury map        # region map: how the build treats each byte
python -m buusfury rommap     # independent structural map of the image
python -m buusfury lift       # rebuild + compare one reconstructed unit
python -m buusfury doctor     # which toolchains are present
python -m pytest tests -q     # portable test suite
```

Reconstruction work is validated at three independent levels, and the project
never infers one from another:

| Verdict | Question it answers | How |
| --- | --- | --- |
| semantic | does the reconstruction behave like the original? | run it on the host and assert the results |
| modern build | does it compile, link and emit bytes? | a modern ARM toolchain, at the original address |
| original match | does it reproduce the original compiler's output? | blocked: needs the original compiler |

Results that need the commercial compiler are reported as blocked with the exact
command that would run them, never as passing.

## Repository layout

| Path | Purpose |
| --- | --- |
| `src/` | reconstructed source, one file per translation unit |
| `src/probes/` | probe entry points and the host self-checks that prove behaviour |
| `include/` | shared declarations and types |
| `config/` | ROM identity, region map, function inventory, reconstruction evidence |
| `tools/` | analysis, build, comparison and progress tooling |
| `tests/` | portable tests for the tooling, the map and the reconstruction |
| `docs/` | architecture, methodology and per-subsystem write-ups |
| `scripts/` | one-command entry points and CI helpers |
| `data/` | a small number of generated fixed regions |
| `.github/` | CI and progress reporting |

## Contributing

Contributions are welcome - reconstructed functions, corrections backed by
evidence from the image, tooling, and documentation.

Start with [`CONTRIBUTING.md`](CONTRIBUTING.md). The short version: pick a
function whose boundaries are already established, write it in `src/`, prove its
behaviour with a host self-check, and run the focused checks rather than the whole
suite.

Two rules matter more than any others: **never commit game data or extracted
assets**, and **do not claim a match you cannot demonstrate**.
